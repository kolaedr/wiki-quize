# WikiQuize — концепт-документ

*Платформа ігор-квізів на даних Вікіпедії/Wikidata. Версія 0.3, 22.07.2026.*

---

## 1. Ідея одним абзацом

Це вже не «один квіз», а **платформа**: набір ігрових механік (свайп, вибір з варіантів, стрічка часу) × набір тем (датасетів з Wikidata). Гравець грає в короткі сесії на телефоні; зареєстрований користувач може **створити власну гру**: обрати тему, підтягнути дані з Вікіпедії, обрати механіку і стиль — і опублікувати. Факти редагувати не можна (тільки те, що каже вікі, з лінком на статтю), тому контент лишається валідованим. Мультимовність: EN базова, далі UA, DE, ES, FR.

## 2. Ключова абстракція: Тема × Механіка = Гра

Це серце архітектури і відповідь на «флексібл ігри». Три незалежні поняття:

**Тема (Topic / Dataset)** — набір сутностей з Wikidata + мапінг полів. Приклад: тема «Країни» = сутності-країни з полями `назва (5 мов)`, `прапор`, `столиця`, `населення`, `площа`, `континент`. Тема нічого не знає про геймплей — це просто дані.

**Механіка (Mechanic)** — код у застосунку, який вміє рендерити картку і приймати відповідь. Кожна механіка декларує, **які поля їй потрібні**:

| Механіка | Потрібні поля | Приклад |
|---|---|---|
| `swipe-binary` | label + 1 порівнюване поле | «Правда/брехня» свайпом |
| `choice-image` | label + image | пише назву → 4 прапори на вибір |
| `choice-label` | image + label | показує прапор → 4 назви на вибір |
| `higher-lower` | label + числове поле | «населення більше/менше?» |
| `timeline-ribbon` | label + дата | стрічка часу: клік на слот → варіанти, що там стоїть (як в оригіналі history-in-cards, але навпаки: обираєш з варіантів для слота) |

**Гра (Game)** — публікована комбінація: `Тема + Механіка + конфіг` (напрямок питання, розмір колоди, рівень складності, стиль/обкладинка). Тема «Країни» автоматично «розблоковує» всі механіки, чиї вимоги покриті полями: прапор→назва, назва→прапор, населення higher-lower, столиці choice тощо.

Додати нову гру = нуль коду. Додати нову механіку = один React-компонент + декларація вимог. Це і є «щоб теми підвантажувати було просто і створювати гру».

## 3. Стек

| Шар | Вибір | Чому |
|---|---|---|
| Фреймворк | **Next.js (App Router) + TypeScript** | один деплой на Vercel: фронт + API + крони; Python не потрібен — інджест даних пишемо на TS у тому ж репо |
| База | **Neon Postgres** (через Vercel Marketplace) | Vercel Postgres закрито, Neon — його офіційний наступник; serverless, безкоштовний tier, branching для дев-гілок |
| ORM | **Drizzle** | легкий, serverless-friendly, SQL-подібний, drizzle-kit для міграцій + Drizzle Studio подивитись дані. (Prisma — теж ок, якщо звичніший; «прізма» — це не база, а ORM поверх того ж Postgres) |
| Auth | **Better Auth** | сучасний стандарт 2026 для Next.js: email+password та OAuth (Google/GitHub), ролі з коробки, схема живе у нашому ж Drizzle/Postgres, безкоштовно і self-hosted |
| Стан/UI | zustand, Tailwind, shadcn/ui (адмінка), **motion (framer-motion)** для свайпів | див. §7 |
| Інджест | TS-скрипти як Vercel Cron + route handlers | той самий код-бейз, без окремого сервера |
| Кеш | Next.js `unstable_cache`/ISR + CDN | колоди генеруються з БД і кешуються |

## 4. Модель даних (чернетка)

```
users            id, email, name, role (player|creator|admin), created_at
topics           id, slug, title(jsonb per-lang), source_config(jsonb: SPARQL/класи/властивості),
                 field_schema(jsonb), status(draft|syncing|ready|published|disabled),
                 owner_id → users, sync_at
topic_entities   id, topic_id, wikidata_qid, labels(jsonb), values(jsonb: числа/дати/uri),
                 image_url, image_credit(jsonb), wiki_links(jsonb per-lang),
                 sitelinks, pageviews, difficulty_score, excluded(bool)
games            id, topic_id, mechanic(enum), config(jsonb: напрямок, deck_size, складність),
                 style(jsonb: кольори, обкладинка), title(jsonb), owner_id,
                 status(draft|pending_review|unlisted|published|blocked), plays_count
sessions         id, game_id, user_id?, seed, score, answers(jsonb), finished_at   -- статистика/daily
reports          id, entity_id?, game_id?, reason, user_id?, created_at, resolved
import_jobs      id, topic_id, status, progress, log(jsonb), started_at
```

`difficulty_score` — перцентиль популярності сутності (sitelinks + pageviews) всередині теми. Звідси градація складності безкоштовно: easy = топ-30% відомих, hard = хвіст. Плюс для числових механік складність = близькість значень (вгадати, хто більший — Китай чи Монако, легко; Іспанія чи Аргентина — складніше).

**Пов'язані теми:** у сутностей є класи Wikidata (P31/P279) і спільні властивості → рахуємо перетини між темами і показуємо «схожі ігри» + можемо збирати кросс-тематичні колоди.

## 5. Інджест даних (без Python)

Все на TypeScript всередині Next.js-проєкту:

1. Творець теми задає джерело: пошук класу Wikidata (автокомпліт через `wbsearchentities`) або готовий пресет (країни, міста, картини, фільми...).
2. Route handler ставить `import_job`, Vercel Cron (або одразу background function з `waitUntil`) виконує його **чанками**: SPARQL по 200–500 сутностей → нормалізація → upsert у `topic_entities`. Чанки — бо serverless-функції обмежені за часом; job зберігає курсор і продовжує наступним тіком.
3. Фільтри якості ті самі, що в v0.1: sitelinks ≥ N, pageviews-поріг, лейбли в усіх активних мовах, обов'язкові поля механік, точність дат ≥ рік, «preferred» ранг при кількох значеннях.
4. По завершенні — **звіт валідації**: «знайдено 195 сутностей, у 189 є прапор, у 195 населення → доступні механіки: choice-image, choice-label, higher-lower». Творець бачить, які ігри може створити з цієї теми.
5. Ресинк тем — кроном раз на 1–2 тижні, підхоплює правки з вікі.

Запити до Wikimedia — тільки server-side, з тротлінгом і власним User-Agent. Клієнт ходить лише у нашу БД/кеш; картинки — hotlink мініатюр Commons з credit-метаданими.

## 6. Користувачі та UGC-флоу

Ролі: **guest** (грає без реєстрації), **player/creator** (зареєстрований — це одна роль, будь-хто може створювати), **admin**.

### 6.1. Гість → реєстрація

Грати можна одразу, без жодних бар'єрів. Прогрес гостя (результати, стріки) живе локально (localStorage/IndexedDB). **Після першої завершеної гри** — м'який, некритичний prompt на екрані результату: «Зареєструйся, щоб зберігати результати, ділитись і створювати власні ігри» (закривається, більше не нав'язується — хіба ненав'язливий пункт у меню). При реєстрації локальні результати **мігрують в акаунт**, щоб гість нічого не втратив.

### 6.2. Кабінет користувача

Один кабінет на всіх зареєстрованих, дві вкладки:

- **Мій прогрес**: результати, стріки, daily-історія, улюблені ігри.
- **Мої ігри**: список створених ігор зі статусами (`draft` → `pending_review` → `unlisted`/`published`), по кожній — звіт валідації теми (скільки сутностей, покриття полів/мов, доступні механіки), причина відхилення якщо було, кнопки «редагувати стиль», «переглянути тему» (список сутностей з можливістю виключати), «подати на публікацію».

Флоу створення гри (візард):

```
Тема:  обрати існуючу  ──────────────────────────────┐
       або створити нову → джерело → імпорт → звіт ──┤
                                                     ▼
Механіка: список доступних для цієї теми (за полями) + напрямок питання
                                                     ▼
Конфіг і стиль: назва гри, складність, кольори/обкладинка, розмір колоди (в межах лімітів)
                                                     ▼
Прев'ю: зіграти самому → подати на перегляд (pending_review)
```

Гарантія валідності UGC: творець **не може редагувати факти** — тільки виключити окремі сутності зі своєї теми (excluded) і оформити подачу. На кожній картці — лінк на статтю Вікіпедії. Скарги гравців (`reports`) летять в адмінку; N скарг на сутність → авто-виключення до розгляду.

### 6.3. Ліміти проти сміття

Обмеження зашиті в систему, а не в модерацію — щоб сміття не виникало, а не щоб його розгрібати:

| Що | Ліміт (стартові значення) |
|---|---|
| Колода на сесію | 7–20 карток (дефолт 10); творець обирає в цих межах, не більше |
| Мін. розмір теми під механіку | choice-варіанти: ≥ 40 сутностей (щоб дистрактори не повторювались), swipe/higher-lower: ≥ 30, timeline: ≥ 50 |
| Макс. розмір теми | ≤ 5000 сутностей (і таймаути, і осмисленість) |
| Тем на творця | 3 активні (не disabled) на старті; піднімається за історією якісних публікацій |
| Ігор на творця | 10; на перегляді одночасно — 3 |
| Імпортів на добу | 5 запусків на творця (SPARQL недешевий) |
| Дублікати | нова гра з тією ж парою тема+механіка+напрямок, що вже в каталозі — блокується, пропонується існуюча |

Ліміти — конфіг у БД, не константи в коді: крутити без деплою.

### 6.4. Модерація: зручний аппрув

Нові UGC-ігри після подачі — `pending_review`; до аппруву доступні як `unlisted` (грати за прямим лінком можна — творець може показати друзям і потестити). Черга в адмінці заточена під швидкість: одна сторінка на гру — **зіграти прев'ю прямо в черзі** (та сама ігрова в'юха, вбудована), поруч звіт валідації теми, семпл з 20 випадкових карток списком (швидко проглянути очима без гри), історія творця (скільки публікацій/відхилень/скарг). Дії: Approve → `published` / Залишити unlisted / Reject з причиною (шаблони причин) — творець бачить причину в кабінеті. Ціль — ≤ 1 хв на рев'ю гри на перевіреній темі; нова тема — головний об'єкт уваги, гра поверх готової теми аппрувиться майже автоматично.

## 7. Клієнт і UX

- **Ігровий екран = один в'юпорт.** App-shell на `100dvh`, `overflow: hidden`, safe-area insets; картка і контроли завжди вміщаються, жодних скролів під час гри. Скрол існує тільки в каталозі/налаштуваннях.
- **Свайп — не Swiper.js.** Swiper — це бібліотека каруселей, для ігрової механіки вона зайва і заважатиме (своя пагінація, DOM-структура). Правильний інструмент — `motion` (framer-motion): `drag` + пороги + fling-фізика + стек карток «наступна визирає з-під поточної». Це ~100 рядків свого коду з повним контролем над відчуттям.
- Кожна механіка — свій компонент (`mechanics/ChoiceImage.tsx`, `mechanics/TimelineRibbon.tsx`...), спільний контракт: `deck in → answers out`. Кнопки-дублери і клавіатура для десктопа/доступності.
- PWA: манфіест + кеш зіграних колод, щоб почата гра переживала втрату мережі.

## 8. Адмінка (мінімальна)

Своя route group `/admin` під роллю admin, на shadcn/ui-таблицях. П'ять екранів, більше не треба: **Черга рев'ю** (див. §6.4 — головний екран), **Теми** (список, статус синку, запустити ресинк, publish/disable), **Ігри** (каталог/unlisted/blocked), **Скарги** (черга, resolve/виключити сутність), **Джоби** (лог імпортів, ретрай). Для «подивитись у базу руками» — Drizzle Studio локально, у прод-адмінку це не тягнемо.

## 9. Мультимовність

Без змін відносно v0.1: сутність у грі лише якщо є лейбли всіма активними мовами (це й фільтр якості); шаблони питань локалізуються вручну під кожну мову (відмінки/артиклі); UI — `next-intl`. Колоди ідентичні між мовами → daily challenge глобально чесний.

## 10. Ліцензії

- Wikidata — CC0, вільно.
- Тексти Вікіпедії — CC BY-SA: атрибуція = лінк на статтю на картці (він у нас і так центральна фіча).
- Зображення Commons — зберігаємо `image_credit` (автор, ліцензія з `imageinfo`) і показуємо по тапу на зображення.

## 11. Ризики

| Ризик | Мітигація |
|---|---|
| UGC-сміття в каталозі | ліміти-запобіжники (§6.3) + pending_review з аппрувом (§6.4); факти незмінні за побудовою |
| Serverless-таймаути на імпорті великих тем | чанковані джоби з курсором + cron; ліміт розміру теми (напр. ≤ 5000 сутностей) |
| Спірні факти, неточні дати | фільтри precision/rank в інджесті; мін. розрив значень для порівняльних механік; репорти |
| Погане покриття лейблами не-EN мов | вимога лейблів на вході; метрика покриття у звіті валідації теми |
| Холодна БД / вартість | Neon free tier + агресивний кеш колод на CDN; читання гри не б'є в БД |

## 12. Roadmap

**Етап 1 — ядро (без UGC):** Next.js + Neon + Drizzle + Better Auth; інджест-пайплайн з пресетами тем (Країни, Історичні події, Винаходи); 3 механіки: `choice-image` (прапори!), `swipe-binary`, `higher-lower`; ігровий екран без скролів; адмінка: теми + джоби.

**Етап 2 — платформа:** `timeline-ribbon`, кабінет користувача (прогрес + мої ігри), гість→реєстрація з міграцією локальних результатів, візард створення гри, черга рев'ю з прев'ю-грою, ліміти-запобіжники, скарги, daily challenge + шеринг, UA як друга мова.

**Етап 3 — зростання:** DE/ES/FR, пов'язані теми і рекомендації, адаптивна складність за статистикою відповідей, лідерборди, дуелі на спільному seed.
