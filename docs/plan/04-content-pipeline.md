# Контент-пайплайн v2 — «розвідка → поля → пари → публікація»

*Карта руху після архітектурного фідбека (2026-07-23). Мета: адмін будує тему
від РЕАЛЬНИХ даних, а не від знання P-ідентифікаторів напам'ять; ігри —
свідомо зібрані пари, публікація — явна дія.*

## Що вже є і лишається (двигун)

- `TopicDef` → генерація SPARQL з полів (`src/lib/ingest/def.ts`) ✅
- Автогенерація ігор з типів полів (image/entityRef/number/date) ✅
- Enrichment лейблів зв'язаних сутностей ✅
- Рівні за складністю, валідація картинок, safe-sync, min-items ✅
- Браузер айтемів з вимиканням, прев'ю unlisted ✅

Проблема НЕ в двигуні, а у **флоу**: вибір полів наосліп, ігри автостворюються
й автопублікуються, розвідки немає.

## Цільовий флоу (4 кроки)

### Крок 1 — Розвідка (probe), нове
Адмін вводить/шукає клас сутності («країна», «модель авто») →

- **COUNT-запит**: скільки айтемів існує при різних порогах sitelinks
  («поріг 60 → 178, поріг 30 → 214») — живий фідбек до повного проходу;
- **Дискавері властивостей**: по топ-50 сутностях — які властивості реально
  заповнені: назва властивості, тип (Commons-媒іа → image, Quantity → number,
  Time → date, Item → entityRef), **покриття %**;
- **Прев'ю однієї сутності**: один запит топ-айтема з реальними значеннями;
- покриття sitelinks по активних мовах (лінки на статті).

### Крок 2 — Вибір полів
Замість ручного вводу P18 — **чекбокси** по списку з розвідки (ролі
підставляються з назв властивостей; ручний додаток лишити як advanced).
Запуск повного проходу → база сутностей + карта полів (validationReport,
вже є). Звіт «отримано X з Y існуючих; відсіяно: лейбли A, поля B, картинки C».

### Крок 3 — Композиція ігор (пари)
Система пропонує **всі можливі пари** з обраних полів з прогнозом кількості
айтемів (алгоритм = розширений autoGamesFor):

| Пара | Тип гри |
|---|---|
| label ↔ image | вгадайка (обидва напрямки = лейаути) |
| label ↔ entityRef | «чиє?» прямий і зворотний |
| number × number | більше/менше |
| date | правда/ні (раніше/пізніше), пізніше — timeline |

Адмін чекбоксами обирає, які ігри створити, **редагує назви** (en/uk),
розмір колоди. Створюються як `unlisted`.

**Важливо (фідбек клієнта 2026-07-23):** одна логічна пара = **одна гра**,
а сінгл/дабл/мульті — це лише варіанти відображення (лейаут — налаштування
гравця). Композитор не має плодити «різні ігри» для труфолс/2/4 варіантів
однієї й тієї ж пари, і каталог має показувати їх як одну гру. Зараз частина
сідових ігор виглядає як дублікати в розмитих категоріях — це наслідок
автогенерації, композитор пар це виправляє.

**Правило зображень:** якщо айтем (сутність або зв'язана сутність-референс)
має зображення — воно **завжди** використовується на картці, текст лише
підпис. Для референсів це означає крос-топікове збагачення: наприклад, у грі
«модель → марка» варіанти-марки показуються з логотипами (P154/P18 через
enrichment), навіть якщо марки — інша тема. Двигун колод це вже підтримує
(`EntityRef.image`), композитор має гарантувати, що enrichment тягне
зображення для всіх entityRef-полів.

### Крок 4 — Публікація (явна)
Ігри НІКОЛИ не публікуються автоматично. Адмін грає прев'ю → «Опублікувати».
Ресинк теми не змінює статуси існуючих ігор (вже так). Min-items лишається
жорстким ґейтом на публікацію.

## Фази реалізації

**Фаза A — розвідка + кінець автопублікації (перша ітерація):**
- [ ] probe-модуль: `countForClass(classQids, threshold)`,
      `discoverProperties(classQids, sample=50)` (тип + лейбл + покриття),
      `sampleEntity(classQid)`
- [ ] NewTopicForm → двокроковий: клас → таблиця властивостей з чекбоксами
      і лічильником; поріг sitelinks зі свіжим COUNT
- [ ] імпорт створює ігри тільки `unlisted` (нові); публікація — кнопкою
      (у ресинку вже опубліковані не чіпаються)
- [ ] звіт «X з Y існуючих» у validationReport і в адмінці

**Фаза B — композитор пар:**
- [ ] сторінка теми в адмінці: секція «Можливі ігри» (пропозиції пар з
      прогнозом айтемів), чекбокси + редагування назв → створення
- [ ] редагування назви/конфігу існуючої гри
- [ ] пошук класу за назвою (`wbsearchentities`) замість вводу QID
- [ ] групування геймплей-варіантів однієї пари в одну гру (каталог показує
      одну картку гри; лейаут — вибір гравця)
- [ ] enrichment зображень для всіх entityRef-полів (логотипи/фото
      референсів), щоб правило «зображення завжди преферед» працювало
      на живих даних, а не лише в сідах

**Фаза C — масштаб і UGC (зливається з етапом 2):**
- [ ] чанковані джоби з курсором для великих класів (>2000)
- [ ] той самий візард для creator-ів за лімітами + рев'ю-черга
- [ ] пресети «Країни»/«Автобренди» переїжджають на цей же флоу
      (лишаються як прибрані шаблони кроку 1)

## Відомі побутові речі (не архітектура)

- «38 країн» — це сід; живий імпорт дасть ~200 (розвідка зробить це видимим).
- Лінки на вікі в сіді моделей — приблизні; живий пайплайн тягне справжні
  per-locale. Розвідка показує покриття лінків до імпорту.
